PRODUCT DECISIONS / 我的产品判断

把 AI 的灵活性，放在合适的位置。

01

稳定背景固定给，详细资料按需取。

机构定位和能力摘要稳定、简短，情报解析直接带入；历史项目和知识材料随任务检索，避免无关信息占据上下文。

对应实现：能力摘要 + 按用途、权限组织的知识检索。商机推进分析可结合业务记录与检索片段。
02

固定流程兜底，动态判断处理变化。

已知任务走固定步骤；工具负责读取业务对象或执行明确操作；模型用于提取、研判与有限步骤规划。创建、阶段和字段变更保留确认。

对应实现：工作流与静态计划、工具调用、受动作白名单约束的动态计划、写入确认卡。
03

事实决定写什么，模板决定怎么写。

客户背景、沟通与政策是事实依据，历史案例提供方法参考，模板只提供章节结构。预算和周期未知时，保留待补充。

对应实现：材料按业务对象组织上下文与检索，分段生成、定向修改并导出 Word。

ITERATION / 从问题到可检查的改进

提到客户，为什么不能直接创建商机？

已有回归输入新增客户，但先不要建商机预期：只创建客户，保留人工确认。
01 / 问题

客户建档与商机创建混在一起。

只有客户关系、没有具体项目时，也可能生成空商机；重复提交已有客户还会造成重复建档。

02 / 原因

语义边界与数据兜底都不完整。

创建意图未充分区分客户和商机；同名检查依赖前端缓存与名称严格相等，服务端缺少去重保护。

03 / 调整

先分意图，再复用对象与确认。

拆分客户与商机创建，补充否定和指代规则；统一名称规范化，服务端复用有权访问的已有客户，确认后写入。

04 / 实际检查结果

检查的是记录行为。

回归检查区分纯客户、显式商机、否定创建与指代请求。开发记录显示：同一测试客户连续创建两次返回同一 ID，同名数量保持 1。

MY CONTRIBUTION / 从设计到交付

我把业务问题拆开，也把交付接起来。

需求与范围

梳理营销和项目管理流程，用 PRD 明确用户任务、优先级和功能边界。

产品与流程

设计线索、客户、商机和材料之间的关联，明确 AI 输出与人工确认的交接点。

实现与部署

通过 AI 辅助开发推进代码实现、部署与演示，让设计成为可操作的系统。

检查与迭代

结合业务反馈定位原因，调整流程和判断规则，用具体输入与记录行为检查改进。

技术如何支撑这些业务任务 ＋

原生 HTML / CSS / JavaScript 前端与 Node.js 服务承接业务操作，MongoDB 和文件存储保存对象与资料。关键词和向量混合检索、重排为相关任务提供参考；会话与账号上下文帮助理解追问，权限控制约束可访问的业务内容。

情报解析、商机分析和材料生成采用各自的调用路径。产品设计将技术连接到“读什么、判断什么、谁确认、写到哪里”这些具体任务。
